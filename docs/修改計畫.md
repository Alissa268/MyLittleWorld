## 0. 這份計畫的用途

這次**不採用一次大改完**的方式。

`New_Android_Backend` 是唯一修改中的版本；`Android_Backend` 保留為可比對、回退的基準；舊 `feat-dept-doctor-recommendation` 設計與 `AILogic/scoring.py` 只作為參考，**不能整包搬回來**。目前 GitHub 已無同名 `feat-dept-doctor-recommendation` 分支；比較舊醫師推薦時以可取得的舊程式、整合紀錄與 `Android_Backend` 為據，不假裝該分支仍存在。

整個改造必須採用：

**修改一階段 → 本機測試 → 上傳 GitHub → ChatGPT 檢查程式碼與 diff → 必要時補修 → 判斷是否需要實機測試 → 通過後才進下一階段。**

禁止 Codex 一次跨多個階段重構。

**本次審查的施工界線（2026-10-14 更新）：** Phase 1～5 的功能驗收基線仍保留，不重做已通過的醫療流程設計；但目前開啟一次性的 **Architecture Cleanup Gate（架構清理閘門）**，只允許移除違反 AI-first 原則的 legacy／duplicate／dead production path（舊版、重複、已無必要的正式執行路徑）與已被 310 真實測試證實的 regression（回歸問題），**不得藉此新增醫療規則、重做 TTAS／官方 KB／SQL schema 或跨階段新增功能。** Phase 6 Backend 已完成主要實作，現處於 310 Backend 驗收中、尚未封存；Architecture Cleanup Gate 通過後才完成 Phase 6 驗收，再進 Phase 7。

**最小修改原則（2026-10-14 新增）：** 任何一般 Bug 修復都必須優先採用 **最小可驗證變更**。只處理已由實測、測試或明確程式控制流證實的直接根因；不得因「順便整理」、「架構看起來更漂亮」、「預防尚未發生的問題」或其他與本次 Bug 無直接因果關係的理由擴大修改範圍。修改前必須先能回答：①實際現象是什麼；②哪個控制流／函式直接造成；③最小修法是什麼；④哪個針對性測試可以證明修復。若單一 Bug 預計需要修改超過 **3 個 production（正式執行）檔案**、新增 service／abstraction（服務／抽象層）、修改 API schema（API 資料格式）或 state machine（狀態機），必須先停止施工，向使用者說明為何最小修法仍不足，取得明確同意後才能擴大。**Architecture Cleanup Gate 例外於「3 個檔案」限制，但只允許刪除或修正本計畫已明確列出的違規 legacy／duplicate／dead production path 與已證實 regression；不得藉 Cleanup Gate 順便重構其他正常模組。** 發現其他問題時先列入待辦，不得在同一次 Bug 修復中順手處理。

**階段分工（2026-10-07 再修訂）：** Phase 1～5 一直是先完成 Backend，Android 尚未同步改造；**Phase 6 同樣只開發、檢查、測試 Backend，不修改 Android、不執行 Android 測試、不把前端整合設為 Phase 6 驗收門檻。** Phase 7 才開始 Android 的資料串接、既有推薦頁／分數顯示調整、對話體驗及整合實測。

**後端介面保守原則：** Phase 6 雖不管前端實作，仍須維持 `/chat`、`/recommend`、`/generate_script` 目前對外欄位、層級、型別與正式掛號 ID；以 **Backend API 契約測試**防止無意破壞。這只是「未來 Phase 7 有穩定介面可接」的保護，**不代表 Phase 6 要替目前尚未改造的 Android 保證畫面已能正常運作**。若新 UI 需要大改資料格式，留到 Phase 7 雙端協調；Phase 6 不偷改既有 API。

# 1. 最終目標

最終系統不再是「7 個固定問題填完後一次決定科別」，也不再是「規則先猜、規則覺得懂了就不叫 AI」。

期望完成後的核心流程：

```text
使用者用自然語言聊天
        ↓
AI 理解本輪訊息
        ↓
將新資訊整理成結構化 evidence
        ↓
Backend 驗證 AI 的 evidence 是否真的來自使用者原文
        ↓
查詢官方醫療知識來源
        ↓
建立 / 更新候選科別
        ↓
候選仍有歧義？
   ┌─────────────┴─────────────┐
   ↓                           ↓
  有                           無
   ↓                           ↓
AI 根據目前歧義          確認正式 dept_id
產生下一個自然追問             ↓
   ↓                      SQL 真實班表
下一輪使用者回答               ↓
   └──────────────→      真實醫師候選
                              ↓
                  已驗證時間限制、偏好排序
                              ↓
                  醫師去重後 AI 專長匹配
                              ↓
                         Backend 驗證
                              ↓
                          推薦掛號
                              ↓
                    generate_script / Android
                              ↓
                    Accessibility 導引
```

候選仍有歧義時的收斂分支（2026-10-27 修訂，詳見第 9 節「線索題收斂」與 Phase 2）：

```text
官方檢索到的全部候選科別
      ↓
後端算出「候選科別的區分概念、使用者未提過」→ AI 以官方用詞出線索題（最多 5 題）
      ↓
使用者回答 → concept_answers（present／absent／uncertain）→ 語意證據 → 計分
      ↓
AI resolved／只剩 1 科／沒有可問線索／達 5 題 → 依最高分決定
平手 → 多問 1 題平手科別獨有線索 → 仍平手 → 家庭醫學科
      ↓
使用者按確認後才進入 SQL 真實班表／推薦（沿用上方主流程）

安全網（步驟 11）：候選為空等線索規則無法決定時，第 8 輪主動詢問一次、第 20 輪上限
```

（舊版「聊到約第 8 輪仍無法收斂才詢問／依官方便民手冊建議家庭醫學科」的主要收斂流程：2026-10-27 起由線索題收斂取代，見第 9 節「線索題收斂」。）

急迫性則是另一條獨立流程：

```text
使用者自然語言
      ↓
AI 抽取 TTAS 所需 evidence
      ↓
Backend 驗證 evidence
      ↓
TTAS-based deterministic engine
      ↓
可判定 → 產生 TTAS-based 初步急迫性結果
資料不足 → 在對話中針對缺失資訊追問
```

**科別判斷與急迫性判斷不可混成同一套分數。**

# 2. 最終架構原則

## 2.1 AI 負責「理解人話」

凡是自由文字，例如：

- 「我上禮拜從樓梯踩空，右腳背一直腫，最近走路越來越痛」
- 「最近心臟有時候砰砰跳，偶爾會有點喘」
- 「頭暈像房子在轉，而且耳朵嗡嗡叫」

皆以 AI 作為主要語意理解器。

AI 可負責：

- 症狀抽取
- 身體部位
- 持續時間
- 發作方式
- 疼痛／不適程度
- 功能影響
- 伴隨症狀
- 外傷機轉
- TTAS 可能需要的證據抽取
- 使用者可看診時間，以及「不能／比較希望／備選／無偏好」的語意和先後順序
- 使用者明確指定的科別／醫師
- 候選科別語意比較
- 多輪對話下一題的自然語言生成
- 同科醫師 `specialty_tags` 與使用者症狀的語意匹配

## 2.2 Rule 不再負責「猜使用者意思」

規則的角色改成：

- JSON schema validation
- 欄位白名單
- `source_text` grounding
- confidence threshold
- state machine
- TTAS-based rule evaluation
- dept_id validation
- doctor_id validation（只能採用真正資料庫 ID，不能以姓名補位）
- schedule_id validation（正式推薦必須有對應班表 ID）
- visit_type validation
- SQL schedule validation
- 確定性日曆計算、時段排序及不可放寬條件驗證
- Backend 對外 API 欄位與正式掛號 ID 的相容性檢查（Android 對接留 Phase 7）
- confirmation gate
- recommendation / script state
- fallback 與 error handling

核心原則：

> **AI 做推理，Rule 做裁判。**

禁止重新建立大量：

```python
if "膝" in text:
    ...
if "頭暈" in text:
    ...
```

來取代 AI 對自由文字的理解。

## 2.3 Database 負責「現實事實」

AI 不得決定：

- 哪個科別實際存在
- dept_id
- 哪位醫師實際存在
- doctor_id
- 哪位醫師今天有沒有班
- 初診／複診是否可掛
- Schedule 是否 open
- 是否為 placeholder doctor

這些全部以 SQL Server 為 truth source。

## 3.2 急迫程度依據

不再使用目前自行設計的：

```text
red flag patterns
+
severity 加分
+
duration 加分
+
function impact 加分
+
自創 urgency score
```

改成參考衛生福利部公開之 **TTAS 急診五級檢傷分類**。

官方來源：

- 衛生福利部「新急診五級檢傷分類標準實施」  
  https://www.mohw.gov.tw/cp-3161-26897-1.html
- 衛福部公開之「急診五級檢傷分類基準修正版」相關表格

> **TTAS-based 急迫性初步篩檢**

不要宣稱：

> 「本系統可以取代急診正式 TTAS 檢傷」

因為完整 TTAS 還包含生命徵象、GCS、SpO2、血行動力等可能無法由手機文字取得的資訊。

# 4. 最終對話狀態（依目前實作修訂）

目前已完成的流程，以實際 Backend schema 與已驗收狀態為準；舊文件列出的 `department_ready / confirmed` 只是早期概念，**不得拿來覆寫已驗收的狀態機**。

主流程示意：

```text
collecting（持續收集／安全釐清）
    ↓
waiting_confirmation（已收斂正式科別，等待使用者確認）
    ↓
recommending（已確認，可取得真實掛號推薦）
    ↓
script_ready / done（依既有流程）
```

急迫情境維持 Phase 5 已封存流程，不進一般掛號推薦。`conversation_state`、`confirmed` 與急迫分流的真實狀態皆由 Backend 管理，不讓 AI 或 Android 自行決定。

新增的時間偏好即使採用內部結構，也不得令已完成的科別確認重新退回固定問卷。已確認後若使用者明確修改時間，只修訂適當的時間偏好資料與必要狀態，不重開 Phase 4、Phase 5 的醫療判斷。

**保底流程（2026-10-27 新增）：** 「資訊不足 → 建議家庭醫學科」不新增獨立的流程階段，沿用既有 `collecting → waiting_confirmation → recommending`：家庭醫學科以「待使用者確認的建議科別」身分進入 `waiting_confirmation`，確認後才可 `recommending`。實作細節見 Phase 2，且不得讓 AI 自行宣布 `confirmed`。**線索題收斂的所有決定（最高分、平手後家醫科、`decline_further_questions`）同樣只進 `waiting_confirmation`，見第 9 節「線索題收斂」。**

# 5. AI 每輪應輸出的核心資料

AI 不得直接控制 workflow。

建議 semantic extraction contract：

```json
{
  "extractions": [
    {
      "field": "body_part",
      "normalized_value": "右腳腳背",
      "source_text": "右腳腳背",
      "confidence": 0.98,
      "status": "available"
    },
    {
      "field": "duration",
      "normalized_value": "約1週",
      "source_text": "上禮拜",
      "confidence": 0.93,
      "status": "available"
    }
  ],
  "conversation_summary": "跌倒後右腳腳背持續腫痛，走路疼痛逐漸加重"
}
```

Backend 必須檢查：

```text
source_text 是否真的存在使用者原文
field 是否為 allowed field
normalized_value 是否符合 schema
confidence 是否足夠
```

AI 不得輸出並直接生效：

- `is_complete`
- `stage`
- `confirmed`
- `red_flags_checked`
- `recommendation_generated`
- `script_generated`
- `doctor_id`
- `schedule_id`

# 6. 多輪科別釐清的最終模式

每輪不是問「下一個固定欄位」，而是：

```text
目前有哪些合理候選科別？
↓
它們為什麼無法區分？
↓
還缺哪一項資訊最能幫助區分？
↓
針對該資訊問一個自然問題
```

例如：

```text
使用者：
最近一直頭暈

系統內部：
耳科 / 神經內科 / 一般內科均可能
資訊不足

AI：
你說的頭暈比較像周圍在旋轉，
還是比較像快昏倒、眼前發黑？
另外有沒有耳鳴或聽力變化？
```

下一輪重新做 candidate convergence。

不能第一輪就強迫輸出唯一科別。

**（2026-10-27 修訂）** 「還缺哪一項資訊最能區分」不再交給 AI 自由決定，也不只看收斂 AI 的前幾名：後端以當輪官方檢索到的**全部**候選科別算出「區分概念」清單，AI 只能從中挑線索出題；使用者回答「沒有」也會記成 absent 並排除該線索。上例的「耳鳴／聽力變化」必須是候選科別知識庫中的官方概念才可問。規格見第 9 節「線索題收斂」。

# 8. 醫師推薦的最終模式（2026-10-07 修訂）

## 8.1 保留 Backend 對外推薦格式，前端留給 Phase 7

**既有 `/recommend` 回傳兩欄、每欄最多五筆，且每筆為具體可掛號診次。** 後端持續提供 `recommendation_id`、`dept_id`、`doctor_id`、`schedule_id`、`doctor`、`date`、`session`、`visit_type` 等既有欄位；`/generate_script` 依真實班表重新驗證。

Phase 6 不把回應改成只回「五位不重複醫師」，也不刪 `specialty_first`／`time_first`；**內部對醫師專長去重，不等於對外把同醫師不同班次移除。** 「一位醫師一張卡、可展開多時段」是 Phase 7 前端體驗設計，不在本階段動。

## 8.2 正確的處理順序

```text
使用者確認正式科別
    ↓
SQL 取得真實可掛班表（可能數百筆）
    ↓
先驗科別、醫師 ID、班表 ID、初複診、停診、時間是否仍開放
    ↓
把使用者「絕對不能」的日期時段排除
    ↓
把可接受日期、時段按使用者語意分層（非醫療加權分數）
    ↓
以 doctor_id 整理相同醫師的多筆班表
    ↓
專長評估只看不同醫師及其正式 SQL 專長，不重複評相同班表
    ↓
AI 只輸出 doctor_id + 0～1 專長相符分數
    ↓
Backend 驗證：doctor_id 必在 SQL 候選內、分數合法
    ↓
將每位醫師的分數套回所有合法診次
    ↓
依「專長優先」或「時間優先」排序可掛號的具體診次
    ↓
維持現有兩欄 × 每欄最多五筆的回應與掛號腳本契約
```

## 8.3 兩種排序的中文定義

**專長優先：** 已符合不能排除條件的診次，先看醫師專長語意分數；分數相同，依使用者時間偏好層級，再依實際日期、時段。此分數只代表語意相關程度，**不是診斷正確率、醫師能力評價，也不是醫療必要性**。

**時間優先：** 先遵守不能看診的硬限制，再看使用者明確說出的日期層級與時段層級，最後才比較專長相符分數。沒有設定時間偏好時，以真實最早可掛診次優先。

不再以無醫學／使用者偏好依據的 70% 專長＋30% 時間、15 分／10 分等人工權重來決定排名。**既有 API 數字欄位先保留、維持原本型別與量尺，但新的後端排序不用舊權重計算。Android 目前如何畫星等，不在 Phase 6 修改或驗收；Phase 7 必須釐清這些欄位的顯示意義，不得把語意分數說成臨床準確度。**

## 8.4 時間偏好以「意思」為單位，不以關鍵字為主

使用者可能說：「這週都不行。最好下週二，不然下週三，再沒有就平日都可以；上午起不來，下午最好。」

AI 只負責從本輪文字抽出有原文依據的條件：

- 絕對不可選：明確說「這週不行」「只能下午」「上午完全不行」等，必須有原文支持；不確定時不能亂標成禁止。
- 日期偏好順位：下週二優先、下週三次之，最後才其他可接受平日。
- 時段偏好順位：下午優先；上午若明確不能則排除；夜間未說明不能時不假設該科一定有班，也不擅自宣稱使用者一定願意夜間。
- 未說清的範圍：例如「平日都行」是否包含本週／其他週，不得和「這週不能」矛盾；必要時只問一個會影響結果的澄清問題。

「下週二」這種相對日期由 AI 判斷語意，**Backend 用台灣時區及當輪對話基準日期算成實際日期**；跨週、跨月、跨年、今天是否已過可掛截止時間、SQL 有無週六週日或夜診，全都用程式和 SQL 決定。

若兩個選項互有優劣（例如「下週二夜間」日期優於「下週三下午」，但使用者偏好下午），**不得偷塞 60/40 權重自行斷定哪個好**。優先用一句澄清問題確認「日期重要還是下午重要」；如不需要追問或使用者不回答，仍可呈現兩個符合硬限制的診次，但只說明各自符合哪些條件，不能把臆測順位當作使用者意願。

**硬限制永不偷偷放寬；軟性偏好只依使用者明確允許的備選順序放寬。** 假如只有夜診、使用者明確只可下午，則不得硬塞夜診；應回「目前無符合可掛號時段」並請使用者調整條件。SQL 沒有夜診／週末，自然不會推薦，不在 Python 寫死科別營運習慣。

## 8.5 醫師數量、速度與公平性

SQL 查到 300 個班表，可能只有 40 位醫師；同一 `doctor_id` 的專長只需要評一次。專長完全相同的 SQL 資料可做**內部精確去重**並共用評分；仍以 `doctor_id` 驗證身份，**絕不拿中文專長字串或醫師姓名當作 ID**。

候選很多時不得「SQL 前 10 位做 AI，其餘 30 位改關鍵字猜」；但也**不得為了硬要全評完而串行發數十次 AI 請求，拖垮使用者體驗**。

採可設定的**單次請求總時間預算與候選容量上限**：優先在安全容量內以少量批次處理；超過容量、逾時或有批次失敗時，整批醫師改採**中性專長分數**並按真實班表與時間偏好排序，不讓「剛好排在前面」的醫師佔 AI 便宜。是否值得採多批次，依 310 實測延遲再決定；既有單次 AI timeout 為 8 秒，不能把它誤當成整條推薦流程必定在 8 秒內完成。沒有實測前不宣稱熱門科別一定很快。

## 8.6 AI 無法評分時

AI 不可用、超時、缺專長資料、回傳格式或 ID 不合法：**不要用症狀／醫師專長的中文關鍵字重新猜醫療關聯。** 未取得有效專長評分者採中性值 0.5；如果是整批逾時或容量超標，整批中性化，維持公平。照真實日期、時段和使用者限制排序。

Phase 6 只在 Backend 回傳與紀錄中如實標明「本次未取得可靠的 AI 專長匹配分數，依可掛號時間排序」，不把中性值解讀成醫師專長優劣。**Android 怎麼顯示這個狀態由 Phase 7 負責。**

## 8.7 驗證與畫面說明

AI 只回 `doctor_id`（醫師正式編號）與 `score`（專長語意分數）；中文醫師姓名和專長只是 **SQL 給 AI 參考的文字**，不當作核對身份的鍵。Backend 驗 `doctor_id` 必存在可掛候選、屬同科、`score` 必為 0～1；每筆最終卡片的 `schedule_id` 必存在且與醫師、科別、日期、診次一致。

AI 不需產出病名、中文「命中的專長」或長推薦理由，避免拿自由生成中文當程式驗證依據。Backend 如需保留推薦說明，只引用 SQL 原有專長及已驗證的時間符合情況，不宣稱病人患有哪種疾病。Phase 6 不新增 Android 必須讀取的欄位；未來額外說明欄位在 Phase 7 再議定。

## 8.8 Backend API 契約保持穩定（Phase 6 僅驗後端）

Phase 6 只做後端相容性測試，不進入 Android 原始碼、畫面、ViewModel、打包或 S23 裝置整合。**前五個階段的 Android 尚未同步改造，這個歷史欠項集中在 Phase 7 一次處理，不要用 Phase 6 的前端測試來製造無關的修補。**

- `/recommend` 必須維持 `case_id`、`recommendations.specialty_first`、`recommendations.time_first`、`total_count`、`fallback_departments` 的欄位名稱、JSON 型別與回傳層級；每欄最多五筆，`total_count` 仍是兩欄項目數相加，不是去重醫師數。
- 每筆推薦維持原欄位與型別：`recommendation_id`、`doctor_id`、`schedule_id`、`dept_id`、醫師姓名、日期、診次、`specialty_tags`、`reasons`、`score`、`specialty_score`、`time_score`、`match_reason` 等。`specialty_tags` 對外仍用既有文字格式，不能變成陣列；舊分數欄位保持既有數字量尺與合法取值範圍，不得突然改成字串、狀態物件或順位整數。
- 排名本身改用清楚的「專長優先／時間優先」層級；舊數字欄位若保留作相容用的展示資料，**不能重新拿來決定新排序**，Backend 必須測試兩者不混淆。它們不是疾病診斷率或醫師能力評分；Phase 7 再決定 UI 要顯示什麼與是否移除過時星等。
- `recommendation_id` 必須精確對應一筆正式可掛診次；`/generate_script` 要能按 `schedule_id`／`doctor_id`／日期／時段再驗 SQL；不能把排名的結果變成沒有班表 ID 的抽象醫師。
- 新的多層時間偏好可存於 Backend 已驗證的個案狀態；既有 `preferred_dates`／`preferred_days`／`preferred_sessions` 不刪、不改型別。若 `/chat` 仍接受舊版個案快照，必須防止缺少新欄位的舊快照把後端已保存的硬性時間限制覆蓋掉；用 **Backend request/response 測試**驗證，不需要 Android 測試。
- Phase 6 只產出對 Phase 7 有用的 API 範例與欄位說明（例如 `docs/PHASE6_BACKEND_API_CONTRACT.md`）；**不在本階段建立 Android DTO／畫面對照表或要求 Android 整合通過。**

若發現為了某種新畫面非改 API 不可：先暫存設計、不要在 Phase 6 強行破壞既有契約，將需要同步改的項目記錄為 **Phase 7 待辦**。

- **dept_id 不寫死**：2026-09-29 的 APP/SQL 盤點中，「家庭醫學科(一般門診/戒菸)」為 `1233`（上層「內科」；一般內科為 `1232`）。程式一律以**設定的科別全名**向 SQL 查詢，**恰好 1 筆 active 才採用**，不把 `1233` 硬編進邏輯。
- **保底不是診斷、也不是一般候選**：`fallback_routing_evidence` 只能在上述觸發條件下使用，**不得參與一般候選科別排名**，避免搶走正常症狀的判斷。
- （措辭「資訊不足、無法判斷科別，建議先掛家庭醫學科」：2026-10-27 起由單一設定話術取代，見第 9 節「線索題收斂」。）仍不說「你得了什麼」，不宣稱家醫科一定最適合。
- **區分兩種失敗**：「資訊不足、判斷不了」→ 本保底流程；「科別明確但 SQL 沒班表」→ 只回無班表，**不自動換科**（Phase 6 原規則不變）。
- **急迫優先**：任何時點 TTAS 判定為急迫，直接走急迫分流，不受輪數、保底流程影響。
- **時間偏好**：家庭醫學科視為一般 dept_id，沿用 Phase 6。若沒有明確症狀，AI 專長分數多半為中性 0.5，此時「時間優先」較有意義；兩欄排序仍維持既有 API 契約，不另改格式。

## 線索題收斂（2026-10-27 新增；Phase 2／4 擴充，插隊優先施工）

### 背景

「頭腦昏沉、食慾不佳」問了 8 題仍不收斂。原因：

1. 出題 AI 不知道候選科別。
2. 「沒有」的回答不會減少候選。
3. 沒有後端決定規則。
4. 同輪字面命中時語意證據消失（已由 `2535093` 修正）。

使用者已同意擴大範圍，改用知識庫「線索題」讓追問有效區分科別。本節取代 Phase 2「下一題／停止條件／soft target」中與科別收斂相關的部分，以及把第 8 輪詢問、輪數上限當主要收斂機制的寫法。

### 候選與出題

- **候選範圍＝當輪官方檢索到的全部科別**，不是收斂 AI 的前 3 名。
- 後端計算「候選科別的區分概念、且使用者未提過」清單，排序：
  1. 獨有概念（只屬於一個候選科別）優先
  2. `direct_routing_evidence` 優先
  3. `source_priority`
  4. 問過但沒結論（uncertain）的往後
  5. 字串排序（穩定排序）
- planner 只拿排序後的前 8～10 個概念。
- planner 回傳 `clue_concepts`（1～3 個、同屬一個候選科別），後端驗證：必須在給 planner 的清單內、數量 1～3、同屬一個候選科別。
- 問句必須包含所選概念的官方用詞，可用括號加白話解釋。**只檢查 AI 輸出的問句，不解析病人文字。**

### 回答與計分

- `pending_answer` 擴充 `concept_answers`：每個所問概念記 `present`／`absent`／`uncertain`，由 Turn Interpreter 判斷、Backend 驗證後轉成語意證據。
- 分數＝支持某科的「不同 `present` 原文片段數」；同義詞不重複加分；**`absent` 不扣分**，但該概念視為已問、不再出題。
- 同義詞（約 19 組，如 頭暈／暈眩／眩暈）以「不同原文片段」計分，並允許 `concept_answers` 涵蓋清單內語意相同的概念；**不建人工同義詞對照表**。

### 決定規則

- **A**：線索題最多 5 題，達上限選證據最多的科。
- **B**：同一候選科別的線索最多 3 個合成一題。
- **觸發決定**（任一）：AI `resolved`／線索確認且只剩 1 科／沒有可問線索／達 5 題 → 依最高分決定。
- **C**：平手 → 多問 1 題只屬於平手候選之一的線索（可到第 6 題）→ 仍平手選家醫科。
- 候選為空則不決定，交給步驟 11 安全網（Phase 2 第 8 輪詢問＋第 20 輪上限）。
- **所有決定仍需使用者確認**（進 `waiting_confirmation`，AI 不得宣布 `confirmed`）。
- 急迫優先：TTAS 判定急迫時直接走急迫分流，不受線索題規則影響。

### 家醫科

- 用設定的全名「家庭醫學科(一般門診/戒菸)」向 SQL 查，**恰好 1 筆才採用**，不得寫死 `dept_id`；不是恰好 1 筆時回「資訊不足，無法判斷科別」，不虛構、不改推別科。
- 話術做成單一設定，目前為：「目前的症狀無法明確區分科別，系統建議先由家庭醫學科初步評估。」
- **不得提榮總或便民手冊**；待使用者找到便民手冊頁碼與原文後，另開資料 commit 換成引用來源版本（同時處理 Phase 3「保底知識條目」）。

### 其他

- **D**：第 8 輪詢問、第 20 輪上限保留為安全網（步驟 11），取代程式現行的 `HARD_TURN_CAP=8`／`ABSOLUTE_TURN_CAP=24`。
- **E**：新對話行為 `decline_further_questions`：使用者不想再被問 → 立即用目前證據決定（仍需確認）；平手直接家醫科，不加問。由 Turn Interpreter structured output 判斷，Backend 不用關鍵字解析。
- 部位、持續多久、嚴重度**不恢復成必填**。
- 固定 7 題 batch 問卷不是現行流程，不得恢復。

### Commit 計畫

```text
0  修訂本文件
1  state 欄位 ＋ department_clues.py（集合運算、排序、計分、決定、平手函式，先不接流程）
2  跨輪保留通過 audit 的語意證據（已完成 2535093）
3  Turn Interpreter concept_answers 擴充與轉成語意證據
4  planner 線索模式與驗證
5  決定規則接進流程（含家醫科確認回覆）
6  decline_further_questions
```

每個 commit 單獨跑測試、單獨上傳，依第 10 節 SOP 驗收後才進下一個。

### 重點


之後若 benchmark 證明需要，再加 embedding。

### 保底知識條目（2026-10-27 新增，待施工）

（2026-10-27 再修訂：家醫科保底現行改以設定全名向 SQL 查詢，不依賴本條目，見第 9 節「線索題收斂」；本條目延後到使用者找到 V4 便民手冊頁碼與原文後，另開資料 commit 施工。）

- `concept`：`無法區分之疾病`
- `evidence_type`：新增 `fallback_routing_evidence`（與 `direct_routing_evidence`、`department_specialty_evidence` 區分；於 `meta.enabled_evidence_types` 另行處理，預設**不**參與一般 retrieval 與候選排名，只供 Phase 2 保底流程取用）
- `canonical_dept_id`：以科別名稱對照 SQL 確認（盤點值 1233）
- `source_id`：`vghtpe_patient_guide_2026`（以 V4-1150528 版確認為準）
- `source_url`、`retrieved_at`、`evidence_text`（原文該列）、頁碼：照現有欄位格式填寫，且**必須是實際對照 PDF 原文後的內容**，不得憑摘要或記憶補寫

- 找不到 V4 對應列時：**不得入庫為官方依據**；此時保底流程仍可作為系統 UX 預設，但話術與報告須如實標示為「工程設計選擇，非官方建議」，不得宣稱有院方依據

- AI 不得推薦 KB / DB 都不存在的科別。
- 官方資料沒有足夠資訊時應標示 uncertainty。

| `/recommend` | `recommendations.specialty_first` 與 `time_first`、每欄最多五筆、`total_count` 等舊欄位及型別 | 不改成只回醫師名單；不要求 Android 在本階段實測 |
| 推薦單筆資料 | `recommendation_id`、`doctor_id`、`schedule_id`、`dept_id`、姓名、日期、診次、專長與既有數值／理由欄位 | 不刪、改名、改 JSON 型別或讓 ID 消失 |
| `/generate_script` | 既有請求形狀、依正式班表重新驗證後回腳本 | 不以抽象醫師名替代實際可掛號班表 |

### 6-B　時間自然語言：理解意思，不發明加權

保留舊 `Availability.preferred_dates`、`preferred_days`、`preferred_sessions` 欄位及相同型別。需要擴充時，僅在 Backend 內部新增可選的時間偏好資料；優先共用 `/chat` 現有的語意理解呼叫，**不要為每個日期偏好多發一次 AI**。

AI 抽取、Backend 驗證並保存：

1. **不能的時間**：日期、日期區間、星期或時段；需有使用者原文佐證才可作硬排除。
2. **希望的順位**：第一優先、第二優先、最後備案；可表達同層並列。
3. **適用範圍**：本週、下週、其他平日、只到某日期、某日之後。
4. **未知／衝突**：沒有提到的時段不可自動判為不能，也不可當作使用者已同意；會影響結果時才追問。
5. **原文依據**：每個重要限制都應有可驗證的文字來源；AI 不決定 SQL 是否有班，也不直接改 `confirmed`／stage。

例句「這週都不行，最好下週二，不然下週三；再沒有就其他平日。上午起不來，下午最好。」應保留：本週排除、下週二第一、下週三第二、其他平日第三、上午排除、下午優先。「最好下午」不是「只能下午」。

相對日期由 AI 解釋語意、Backend 根據每次對話當下的**臺灣日期／時區**計算具體日期，不讓 AI 自己猜日期。週六週日、夜診、停診、截止時間都以 SQL 與確定性程式判定，**不預設某科別一定有或沒有夜診與週末診**。

硬限制**絕不私自放寬**；使用者允許的備選才能按順位使用。遇到「下週二晚上」和「下週三下午」這類日期、時段互有優劣，不能擅自做 60/40 或 15 分／10 分加權；必要時透過 `/chat` 問「較重視日期還是下午時段」，在未獲答案時只用有明確依據的順位並以真實日期時間作穩定排序，不宣稱這就是使用者的總偏好。

### 6-C　數百筆班表，不等於數百次 AI

先取真正合法的 SQL 診次，再按 `doctor_id` 去重。**同一醫師不管有幾筆日期／上午／下午診，醫師專長只評一次。** 兩位醫師的正式 `specialty_tags` 完全一致時，可在 Backend 內部共用評分結果，最終每筆診次仍保留原本的 `doctor_id` 與 `schedule_id`。

AI 輸入只限已接受的病人症狀資料、候選醫師正式 ID、SQL 真正專長；不給無關的班表逐筆細節。不照搬舊版「先猜病患得什麼疾病」prompt，只做症狀語意和專長描述的關聯比較。AI 輸出最小化：

```json
{"scores": [{"doctor_id": "7372", "score": 0.82}]}
```

Backend 僅以**正式 SQL `doctor_id`**比對候選身分，不用醫師姓名或中文字串當身份 ID；驗同科、分數是否為 0～1、是否有重複、非候選 ID。最終可選診次必有合法的 `schedule_id`、`dept_id`、日期、時段與初複診資訊。

### 6-D　熱門科別的時間預算、公平性及退路

**禁止**把 300 筆班表當作 300 個 AI 問題，也禁止逐位串行多次呼叫模型。不得只對 SQL 前 10 位醫師用 AI 而讓其餘醫師吃虧。

可設可調整的整體時間預算、每次輸入容量與少量批次上限，用 310 實際測量決定具體數字。不要先保證 40、60 位都能快速評完；更不能無限串行多個 8 秒 timeout。

如果 AI 不可用、超時、回傳不完整或候選量超過公平評估容量，**本次候選整體採中性專長分數 0.5**，依合法真實班表與已驗證時間偏好排序；不讓一部分候選有 AI 加分、另一部分只得中性值。絕不啟用 `SPECIALTY_KEYWORDS`、`_explainable_specialty_matches` 等中文醫療關鍵字作替代醫療推理。無可掛診次就回無班表，不自行換科。

### 6-E　輸出兩種排序，維持既有 API

**專長優先：** 必須先通過全部時間硬限制；正式醫師專長語意分數較高者排前，同分按使用者日期／時段層級、真實時間決定。

**時間優先：** 必須先通過全部時間硬限制；先按使用者明確的日期／時段順位，沒有可比順位時按真實時間，最後才比醫師專長語意分數。不得讓專長分數補償使用者明確不能的時間。

不設人工 70/30 總權重或 +15／+10 的日期分數。**對外依然是兩欄、每欄最多五筆具體診次**，不是一位醫師只占一張卡；同一位醫師不同合法診次可在清單中各占一筆。前端想「一個醫師卡展開所有時段」留 Phase 7。

已存在的 `score`、`specialty_score`、`time_score`、`match_reason`、`reasons` 欄位須**保持原名稱、型別與數字量尺**（`score` 為 0～100；兩個子分數為 0～1），並以 Backend 契約測試保護。**新的排名依據與舊分數顯示欄位分開**：不得因舊數字存在，就又用 70/30 決定新排名；也不能在後端理由裡把 AI 中性分數寫成「專長高度相符」。Phase 7 才處理 Android 星等及描述如何正確呈現新排序，不把 Phase 6 變成 UI 施工。

### 6-F　Phase 6 不做 Android；Phase 7 再完整整合

本階段明確不做：

- Android 程式碼、DTO、ViewModel、推薦卡片、星等、中文推薦描述、選卡動作、語音、無障礙與 UI 測試。
- Android 單元測試、打包、模擬器或實體裝置測試；這些不應成為 Phase 6 第一道失敗門檻。
- 將現有兩欄診次回應改成只回五位醫師，或要求前端立刻支援多時段展開。

**Phase 6 須交付可供 Phase 7 使用的後端 API 契約、樣本和已知介面限制。** 未整合的 Android 本來就可能與 Phase 1～6 的 Backend 行為不同步；這是 Phase 7 工作，不能把它當成 Phase 6 錯誤來回頭修改已封存的後端階段。唯有 Backend 對外欄位被不慎破壞，才是 Phase 6 自身必須修的問題。

### 6-G　後端測試、310 驗收與 GitHub 檢查

1. **SQL 與正式 ID：** 同一醫師多班次、熱門科別多位醫師／數百筆班表；無 `doctor_id`、`schedule_id`、錯科、過時、已停診、初複診不符的項目不進推薦；不拿姓名代替 ID。
2. **AI 專長：** 比較口語症狀與醫師正式專長；同一醫師只評一次；陌生 ID、重複 ID、非法分數、超時與大量候選有一致退路；不能僅評 SQL 前十位；不恢復醫療關鍵字分數。
3. **時間偏好：** 這週不能、下週二→下週三→平日備案、上午不能／下午最好、只下午、跨月／跨年、週末有無診、夜間無診、日期時段順位衝突、截止時間、無符合班表。
4. **排序與 API：** 兩欄排序符合定義；每欄最多五筆、`total_count` 正確、欄位型別和量尺未破壞；每一筆都可用原有 `recommendation_id` 經 `/generate_script` 重新核對真實班表。全部只用 Backend 自動化測試。
5. **310 實機（僅 Backend）：** 直接用 PowerShell／HTTP 測 `/chat`、`/recommend`、必要的 `/generate_script`；包含真 SQL、不同時間偏好、熱門科別、AI 正常與模擬失敗、SQL／AI／總耗時。**不測 Android 畫面或 S23。**

**測試節奏：** 每次小修只跑相關 Backend 測試；Phase 6 功能收尾準備封存時才跑一次 Backend 全套測試與 310 Backend 實機驗收。**不執行 Android unit test／build**。Phase 7 才開始 Android 解析、畫面、選卡和端到端驗證。

16. 不得拿醫師姓名、醫師專長中文文字代替正式 `doctor_id`；不得讓欠缺 `schedule_id` 的診次進掛號推薦。
17. Phase 7 不得讓 Android 用症狀／專長關鍵字自行發明醫療推薦理由，或把中性分數當作準確率／星等保證；這是 Phase 7 的前端整合要求，非 Phase 6 前置門檻。
18. （2026-10-27 新增）家庭醫學科保底流程：不得把 dept_id（如 1233）硬編進邏輯，須以設定的科別全名向 SQL 查詢且恰好 1 筆 active 才採用；話術只能用單一設定文字，資料 commit 前不得提榮總或便民手冊；不得略過使用者確認 gate；不得讓 `fallback_routing_evidence` 參與一般候選排名；不得在缺少官方原文佐證時宣稱有院方依據；不得以關鍵字解析使用者對「繼續描述／先掛家醫科」的回答。

# 13. 最終成功標準

### 對話

- 使用者不用照固定七題回答。
- 可以自然地一段一段補充。
- AI 能根據前文追問。
- 不會一直重問已經知道的事。
- （2026-10-27 新增）不會無止境追問：科別釐清以線索題為主，最多 5 題（平手可到第 6 題），使用者不想再被問可隨時結束；仍無法區分時以單一設定話術建議家庭醫學科，由使用者確認。第 8 輪詢問、第 20 輪上限只是安全網。（舊版「約第 8 輪主動詢問、最多 20 輪」作為主要收斂機制：2026-10-27 起由線索題收斂取代，見第 9 節「線索題收斂」。）

### AI

- 自由文字以 AI 為主要理解器。
- AI 每個重要抽取有原文 evidence。
- AI 不得憑空補病情。
- AI 不得控制 Backend workflow。

### 科別

- 不第一輪強迫唯一選科。
- 能有 Top-K candidate。
- 能因新資訊逐步收斂。
- 判斷依據可追溯到院方公開資訊。
- dept_id 必須來自正式 DB。
- （2026-10-27 新增）無法區分時的家庭醫學科建議必經使用者確認。（「可追溯到榮總便民手冊『無法區分之疾病』一列」：2026-10-27 起改為待資料 commit 補上來源，見第 9 節「線索題收斂」。）
- （2026-10-27 新增）追問能區分候選科別：線索題來自候選科別的官方概念，「沒有」的回答也會讓該線索不再重問。

### 急迫性

- 移除自創 red flag + 自創 urgency score。
- 使用 TTAS-based、可追溯官方 rule。
- 不知道的生命徵象不亂猜。
- 無法完整分級時明確標示資料不足。

### 醫師與時間

- 只從真正可掛號 SQL rows 中選，每筆可選卡片有有效 `doctor_id`、`dept_id` 與 `schedule_id`。
- 同醫師多筆班表不重複送 AI，熱門科別不會因候選量過大而無限串行呼叫模型。
- AI 做專長語意匹配，但不猜疾病、不捏造專長；沒有有效 AI 分數即採一致中性處理。
- 使用者明確不能的日期／時段絕不推薦；第一偏好、次要偏好、備選的順位能保留，無 70/30 自創權重。
- 沒有班表就回無班表，不跨科偷換、不假設每科都有夜診或週末門診。
- `/recommend` 維持既有兩欄具體診次 JSON 契約，Backend 能用 `recommendation_id` 呼叫 `/generate_script`；Android 真正對接及選卡畫面驗收留 Phase 7。

### 系統

- Android 不自行建立第二套醫療／流程／時間排序邏輯，並以 Backend 狀態為準。
- Backend 是 state truth，SQL 是 schedule truth。
- AI failure 不會造成錯誤假推薦；Phase 6 Backend 理由不謊稱專長高度相符，Phase 7 Android 畫面亦不得誤導。
- **Phase 6 只驗 Backend API 與 SQL／AI 推薦；Phase 7 才處理 Android 資料解析、畫面、選卡、UX 和雙端整合。** Phase 6 不破壞現有對外欄位，降低 Phase 7 整合成本。
- 小修跑精準測試；每個完整階段封存前才安排一次全套測試。

### 研究可信度

- 不宣稱「我們自己發明的醫療規則是正確的」。
- 不宣稱臨床準確率。
- 可以展示官方來源、多輪收斂、natural language robustness、hallucination control、rule baseline comparison。

### Architecture Cleanup Gate（一次性架構清理閘門）

本 Gate 只允許做下列工作：

- **刪除 production 中對患者自由文字做語意判斷的 keyword／regex／phrase-list／syntax parser。** 症狀、否定、更正、已回答、要求解釋、指定科別／醫師、時間偏好等自然語意一律由 AI Turn Interpreter 的 structured output（結構化輸出）提出；Backend 只做 schema、source grounding、confidence、正式 SQL／KB identity、TTAS rule、workflow/state 驗證。
- 可保留「AI 輸出品質」的 generic question／information need guard，以及固定初始提示、安全警示、技術錯誤、確認狀態等**不需要理解患者語意**的系統文案；不得把這些固定文案拿來取代已成功辨識的自然對話意圖。
- 科別收斂只能使用已驗證的 structured semantic evidence、官方 KB evidence 與 active SQL Department；AI／Backend 都不得自行發明 `dept_id`。沒有足夠依據時回 ambiguous／unresolved，不得退回患者文字關鍵字猜科。
- 可刪除已無 production caller 的 dead module／compatibility path；刪除前必須先搜尋 caller，並同步清掉只服務該舊路徑的測試、import 與註解。不得刪除仍被 Voice／TTS／正式 API 使用的共用程式。
- 修復已由 310 真實測試證實的 `request_explanation` 控制流：AI 已驗證為要求解釋時，不得再回「無法理解安全回答」；自然解釋仍交由 AI planner 生成並由 Backend 驗證，AI 生成失敗才可走技術性 fallback。
- **不得修改 Android、SQL schema／正式資料、TTAS 官方 rule、官方科別 KB 內容、Voice Gateway、Accessibility 或 secrets。** 若清理需要改這些範圍，必須停止並先回報。

Cleanup Gate 的固定順序：

```text
1. Source-content gate：先確認目前 production 主路徑與舊路徑 caller
2. 小範圍刪除／修改，不跨到 Android 或資料庫 schema
3. targeted Backend tests
4. Backend full suite
5. 上傳 GitHub，由 ChatGPT 檢查實際 diff
6. 310 真 Cerebras + 正式 SQL Backend 重測
7. 全部通過後才封存 Phase 6，進入 Phase 7
```

**目前下一個動作就是 Architecture Cleanup Gate，不再重做 Phase 6-A。** Phase 6-A～6-E 的主要 Backend 實作已存在；這一輪先清除與計畫架構衝突的舊 production path、修正已證實 regression，並確認 `/chat`、`/recommend`、`/generate_script` API 契約沒有被破壞。**不測、不改 Android。**

非功能性整理：目前 GitHub 的 `New_Android_Backend` 曾出現被追蹤的 `backend/.pytest_tmp_full/` 測試暫存檔，應在不碰 Phase 5 功能的獨立整理提交中移除已追蹤產物，並在 `.gitignore` 忽略 `**/.pytest_tmp*/`。**這不是 Phase 5 重開，也不應與 Phase 6 功能修改混在一個難審查的大提交。**
